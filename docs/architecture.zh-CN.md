# Jev Scout 架构

[English](architecture.md) | [简体中文](architecture.zh-CN.md)

[项目介绍](../README.zh-CN.md) · [路线图](roadmap.zh-CN.md) · [Demo 指南](demo.zh-CN.md)

Jev Scout 在编码代理尝试修改代码之前，调查代码仓库并生成可检查的证据。M1 实现了只读、离线的规则基线；M2a 加入可选的 Jev 候选选择器；M2b 加入显式证据恢复和共享输入的策略比较；M2c 加入可选且有上限的同文件相邻扩展；M2d 加入运行过程中可选、由策略选择的上下文恢复。版本 0.5.0 使用 Python 3.11+ 和标准库，不生成修复补丁。

设计将证据收集、有预算限制的工作上下文，以及决定下一步检查内容的策略分开。服务提供方特有的行为封装在策略适配器内，证据管理和来源归属始终由本地运行时负责。

## 当前数据流

```text
任务 + 代码仓库
        |
        v
有上限的扫描 --> 待检查候选
                        |
                        v
               Policy.choose(state, candidates)
                 /                   \
             离线规则             可选 Jev Choice
                 \                   /
                    经验证的决策
                        |
                        v
                经验证的源码读取或上下文恢复
                        |
                        v
                  证据 + 有序事件
                        |
                        v
                有预算限制的工作上下文
                        |
                        v
            events.jsonl / evidence.json / report.md
```

候选指定具体路径、行范围和预期 SHA-256。`restore_observation` 候选还指定同一次运行中已存在的观察记录。策略返回候选 ID、表示停止的 `None`，或携带追踪元数据的类型化 `PolicyDecision`。已有的返回 ID 的策略仍然兼容。调查器会先检查选中的 ID 是否属于当前候选集合，再执行读取或恢复。

发现阶段一次性对文件名和内容的关键词匹配进行排序，建立初始候选集合。默认情况下，该集合保持固定。启用 `--max-followups` 后，一次成功且哈希匹配的读取允许本地运行时在该文件中提供相邻片段。规则策略按确定性规则选择；Jev 根据任务和当前上下文从当前提供的 ID 中选择。两种策略都不能自行生成路径或坐标。启用 `--max-restores` 后，运行时提供被移出上下文的观察，供策略在动作循环内经源码验证后重新使用。独立的恢复命令将显式请求的历史观察投影到新的交接上下文中。跨文件扩展和真实服务验证仍属于后续 M2 工作。观察记录可供人员或未来的修复求解器接手使用。

离线 CLI 保持如下形式：

```sh
scout investigate --repo PATH --task TEXT --output DIR \
  --max-steps N --max-context-chars N --max-followups N --max-restores N
```

加上 `--policy jev` 可启用远程选择。[Jev 策略指南（英文）](jev-policy.md) 定义了配置、传输数据、服务提供方接口契约和回退行为。实现与测试定义了参数默认值、数据结构、排序行为，以及扫描和读取采用的确切限制。

另外两个命令在明确的边界内运行：

```sh
scout recover --evidence PATH --repo PATH --observation ID --output DIR \
  --max-context-chars N
scout compare --repo PATH --task TEXT --output DIR \
  --max-steps N --max-context-chars N --max-followups N --max-restores N --challenger rule
```

恢复命令读取有大小上限的导入文件，并对照显式指定的仓库检查所请求的观察记录。比较命令只发现和捕获一次输入，然后让独立的规则策略和对照策略依次在同一份冻结源码上运行。选择 `--challenger jev` 时，采用与调查命令相同的服务提供方限制和显式启用契约。

## 实现映射

| 模块 | 职责 |
| --- | --- |
| `models.py` | 不可变候选、任务状态、上下文条目、类型化策略决策和结果路径 |
| `repository.py` | 相对目录的源码读取、有上限的发现、词法排序和限定符号窗口 |
| `frontier.py` | 共用的候选容量限制与 ID 分配 |
| `expansion.py` | 有上限的相邻窗口生成、重复候选抑制和父记录关系 |
| `restoration.py` | 被移出上下文的观察对应的一次性、有上限的恢复候选 |
| `source_checks.py` | 显式恢复和运行内恢复共用的哈希与准确片段验证 |
| `investigator.py` | 动作循环、源码有效性、上下文投影、有序事件和输出产物 |
| `jev.py` | 有上限的 TypeSafe HTTP 请求、封闭选项验证、规则回退和决策元数据 |
| `recovery.py` | 有上限的证据导入、源码和片段重新验证、恢复后的上下文和报告 |
| `comparison.py` | 共享快照捕获、独立策略运行、计时、诊断和工作副本重新验证 |
| `cli.py` | 参数解析、面向用户的错误和运行摘要 |

运行时没有第三方依赖。Jev 可替换；持久化仓库记忆和 LLM 修复求解器仍是未来组件。

## 边界与契约

| 边界 | 职责 |
| --- | --- |
| 仓库访问 | 读取源码范围内的本地内容，并限制扫描和读取。 |
| 策略 | 选择读取或恢复候选，或停止；公开服务提供方决策和回退情况，不负责源码读取。 |
| 证据 | 保存观察到的文本及其来源身份，区分观察记录与解释。 |
| 工作上下文 | 在字符预算内选择观察记录，不销毁保留的证据。 |
| 报告 | 展示候选、支持它们的观察记录、限制和停止原因。 |

仓库文本、任务文本、注释和文档都是数据。其中出现的指令不授权执行命令、修改源码或扩大访问范围。规则策略不发起网络请求。显式选择 Jev 时，会将任务、候选描述、相对路径与预览，以及当前上下文传输到固定的 TypeSafe 官方端点。源码内容不能控制该端点或允许执行的动作。

两种策略都不会构建、测试或修改被调查的源码。调查器要求输出目录位于仓库之外，并拒绝覆盖已有结果产物。

安全源码读取当前要求 POSIX 相对目录打开能力和禁止跟随符号链接的支持。M1 会跳过符号链接、非常规文件、超大文件、二进制内容和非 UTF-8 文本。这是有上限的文本基线，被跳过的内容仍构成覆盖范围限制。

## 证据与来源追踪

观察记录始终关联其源码路径和行范围。预期哈希标识调查器原本准备检查的内容；哈希不匹配时，候选读取不能成为观察记录。在最终报告生成前，会再次检查已保存观察记录的来源，并标记已变化或不可用的源码。这是一个时点检查，不保证源码文件在之后仍保持不变。

各产物的作用相互补充：

- `events.jsonl` 记录有序调查事件、可检查的服务提供方请求载荷、决策和结果。
- `evidence.json` 的 schema 3 包含保留的观察记录、工作上下文、策略配置、决策追踪和用量记录。
- `report.md` 面向人工审阅，展示调查结果以及服务提供方和回退的统计。

Schema 3 在此前交接数据基础上增加混合的读取/恢复候选及恢复统计。源码路径、行范围、指纹、观察文本和原始读取事件的含义保持不变。消费方必须先显式支持 schema 3，才能使用新运行的结果；选择一个恢复动作不会生成另一条观察。

M2c 引入 `expansion` 统计和 `generated_candidate_lineage`，schema 3 保留这些字段。有序事件记录新增候选的父候选、成功的父观察记录，以及 `before` 或 `after` 方向。恢复命令可通过现有观察记录契约导入这些调查证据包。

决策追踪区分所请求的后端与实际选择动作的后端。Jev 追踪包含请求和返回的模型标识、有效时的置信度和概率分布、可为 null 的服务提供方 token 用量、耗时毫秒数、调用尝试次数和回退原因。缺失的用量表示未知，而不是零；一次超时仍可能对应服务提供方已执行、但 Scout 无法统计的工作。

凭证、授权请求头、服务提供方的原始错误和异常字符串不会写入产物。请求载荷有意包含源码片段。产物的隐私要求取决于被调查的源码；可检查性不代表私有源码适合公开发布。

保存的观察记录是调查中的片段，不是仓库的完整归档。以后读取同一源码文件时，可能得到不同内容。证据恢复意味着检查保留的观察记录并定位其来源，不意味着自动恢复运行、复现模型答案或重放任意工具副作用。

### 恢复过程的来源追踪

`scout recover` 接受调查 schema 1、2 或 3，导入上限为 16 MiB 和 100 条观察记录。导入内容是数据，不是选择仓库的授权：只有 `--repo` 控制源码访问。所请求记录保留原始文本和来源归属，恢复数据包记录原始产物的 SHA-256。

恢复过程通过现有安全读取边界检查每条所请求记录的来源，再将哈希、行范围、记录的片段和截断标记与当前文本逐项核对。已变化、不可用或片段不一致的记录仍作为历史记录展示，但不能进入当前上下文。匹配的记录进入调查命令同样采用的、有预算限制的 FIFO 上下文投影。产物哈希建立字节之间的关联，不证明作者身份，也不认证原调查器。详见[证据恢复（英文）](evidence-recovery.md)。

### 冻结比较的来源追踪

`scout compare` 只进行一次发现，仅捕获保留的初始候选集合所涉及的完整文件文本，内存上限为 32 MiB。两组策略开始运行之前，每个捕获文件都必须匹配候选的预期 SHA-256。两组共享任务、初始候选、捕获的读取内容、扩展/恢复设置和限制，但分别拥有独立策略状态、上下文和输出目录。相邻扩展和恢复验证使用这些已捕获的文件，不能引入初始捕获范围之外的源码。不同的先前选择可能产生不同的后续候选菜单。

快照 ID 是对任务、相对路径候选、源码哈希与字节数、限制和实现版本计算的规范化哈希。绝对根路径和时间戳不参与计算。捕获有上限且顺序执行，不宣称它是整个仓库的原子状态或某个 Git 版本。

捕获的完整源码只保存在进程内存中。持久化的清单和选中片段无法重建尚未观察的捕获内容，因此以后复现还需要获得原始、获准访问的仓库版本。

冻结输入的两组调查数据包使用 schema 3，带有 `source_mode: "frozen"`、`snapshot_id`，以及观察有效性值 `matched_frozen_snapshot`。观察记录保存 `checked_snapshot_sha256`，并将 `current_sha256` 保持为 null。即使原工作副本在任一组运行期间变化，这些记录描述的仍是匹配的捕获内容。两组都完成后，独立检查会标记工作副本当前内容与捕获哈希之间的关系。源码超链接指向显式指定的工作副本，而它可能在捕获后已经变化；记录的片段仍是当时观察到的内容。

`comparison.json` schema 3 记录发现与捕获耗时、每组完整运行耗时、截至摘要构建的总比较耗时、服务提供方用量和行为诊断。候选与观察 ID 属于各自分支，因此动作身份由种类、相对路径、预期源码哈希、开始与结束行，以及最大片段字符数确定。同一行范围的读取与恢复具有不同的动作种类；重新加入观察不会产生新证据，也不会增加观察重合度。同位置一致率和已观察动作重合度比较这些身份，同时保留分支内 ID 供查找轨迹。总耗时不包含最终摘要文件的发布。这些诊断不衡量定位质量、修复成功率或成本节省。受控测试替身的传输方式会与真实服务提供方调用分开标识。详见[策略比较（英文）](policy-comparison.md)、[ADR 0003（英文）](adr/0003-recovery-and-frozen-comparisons.md)[ADR 0004（英文）](adr/0004-bounded-follow-up-evidence.md)和 [ADR 0005（英文）](adr/0005-policy-context-restoration.md)。

### 有上限的相邻证据扩展

`--max-followups` 默认值为 `0`，接受 0 到 100 的整数。成功记录观察之后，运行时在父候选之前和之后紧邻的位置提出窗口，限定在同一源文件内，每个最多九行。重复的候选身份会被抑制。新增候选继承父候选的预期哈希，分数为 `max(0, parent_score - 1)`，预览最多为 240 字符。每次读取最多保留 4,000 个片段字符，因此即使九行窗口也可能被截断。

配额统计已经纳入的新增候选，而不仅仅统计最终读到的候选。初始、相邻扩展和恢复候选共用 100 个候选的全局上限。所有被选中的动作共用原有的步数预算，生成候选不会重置任何预算。扩展记录新增数量、被抑制的提议以及触及的限制。失败、不可用或哈希不匹配的读取不能成为扩展起点。相邻扩展保留只读边界，不会重新扫描仓库、增加文件、续跑先前的调查，也不会自行恢复被移出的证据。恢复需要单独启用其配额。详见[相邻扩展指南（英文）](follow-up-evidence.md)。

### 由策略选择的上下文恢复

`--max-restores` 默认值为 `0`，接受 0 到 100 的整数。观察被移出工作上下文时，运行时可为它生成一个具体的 `restore_observation` 候选。只有本次运行保留的观察符合条件；当前活跃观察不会重复加入。配额统计已经纳入的候选，包括最终未选中的候选。初始读取、相邻扩展和恢复候选共用 100 个候选的总上限，并具有唯一候选 ID。

重新加入观察之前，本地代码通过安全读取边界核对源码哈希、行范围、准确的已保留片段和截断标记。已变化、不可用或不匹配的证据不能进入活跃上下文。成功恢复会重新使用原观察 ID 和文本，不记录新的原始观察。同样的 FIFO 移出规则和字符截断仍然适用，因此恢复可能移出另一条观察。每条观察最多获得一个候选；它再次被移出时不会生成另一个。

每个被选中的恢复，包括被跳过的恢复，都与读取共用 `--max-steps` 操作预算。规则策略优先选择尚未读取的候选，再选择分数为 `-1` 的恢复候选。Jev 接收每个候选的动作种类及具体源码元数据，恢复候选还包括观察 ID，然后选择所提供的 ID。这不会让服务控制路径、坐标或自由格式动作，也不会增加调用额度。

冻结比较分支对照已捕获的源码验证恢复，分支运行期间不查询当前工作副本。单独的最终工作副本检查仍保持原意。手动 `scout recover` 仍是显式导入并生成交接产物的命令；两种机制都不会续跑此前的调查。有上限的证据重新调用是一项接口能力，尚未证明质量或成本收益。详见[由策略选择的上下文恢复（英文）](policy-context-restoration.md)和 [ADR 0005（英文）](adr/0005-policy-context-restoration.md)。

## 上下文与工作预算

工作上下文预算限制为下一个消费方选择的文本，不保证每个输出产物都符合相同上限。保留证据和纳入上下文是两个独立决定：将观察记录从工作上下文移出，不应悄悄删除保留的原文。

操作步数、扫描、读取和新增候选限制共同约束调查工作。触及限制时，结果必须明确展示停止原因或部分结果的限制。没有候选、文件不可读、内容不受支持和检查不完整，都是应如实披露的有效结果；它们不证明任务无解。

发现过程采用有上限的目录遍历。达到条目上限后，只能对已枚举的前缀排序；其覆盖范围可能受文件系统枚举顺序影响。完整、未变化的测试样例扫描会作出稳定决策，但被截断的扫描不保证跨平台覆盖一致。初始发现为每个匹配文件创建一个检查窗口。可选的相邻扩展可以检查该文件的更多内容，但有限的候选与步数预算，以及片段截断，仍然使整个文件的覆盖无法得到保证。

排序分数估计调查相关性，不认证诊断、不识别每个必需文件，也不预测补丁能否通过测试。M1 不为候选分数附加经过实证校准的正确概率。

## 远程决策边界

Jev 在一个 Choice 问题中接收所有尚未选择的读取与恢复候选，每个候选都附有具体源码元数据。完整序列化后的 UTF-8 请求必须符合配置的请求字节上限，否则 Scout 不发送请求，直接使用规则选择。这会保留候选覆盖范围，避免适配器暗中改变候选短名单。响应体也有固定字节上限。

每次选择最多进行一次 HTTP 尝试。独立的服务提供方调用预算按 `JevPolicy` 实例累计尝试次数，包括失败尝试。CLI 为每次调查创建一个实例；库调用方如果复用实例，也会共享它的预算。传输使用固定 HTTPS 端点，拒绝重定向，不继承代理设置。超时限制的是 socket 操作，不保证整个运行的墙钟时间截止点。

本地验证检查请求的问题及类型、选中的候选集合 ID、分布键、概率与置信度是否为有限数值，以及概率归一化。响应格式错误、服务提供方失败、低置信度、请求超过上限或调用预算耗尽，都会触发显式规则回退。低置信度响应仍可能消耗 token，报告的用量会保留展示。API Key 缺失或格式错误属于调查开始前的配置错误；服务提供方拒绝密钥时，会产生身份验证错误回退。

置信度下限是可配置控制项，默认值为 `0.0`，并非经实证验证的可靠性阈值。TypeSafe 将置信度描述为概率分布集中程度的统计量；它不同于所选选项的概率，也不同于任务成功率。详见[Jev 策略指南（英文）](jev-policy.md)和 [ADR 0002（英文）](adr/0002-typed-jev-decisions.md)。

## 错误与恢复

后续检查失败时，应保留此前成功获得的观察记录。披露受影响的源码或动作，而不是将结果呈现为空的成功。部分结果应公开缺口，便于后续调查者扩大搜索。致命配置错误或产物写入错误，必须与已完成但没有有效候选的调查区分。

显式恢复已经支持根据保留的观察 ID 重建交接上下文，可选的相邻扩展支持有上限的同文件证据扩展，由策略选择的恢复支持在运行过程中有界地重新调用证据。后续 M2 工作应支持跨文件证据扩展、与后续调查的关联，以及真实服务提供方验证。未来的修复求解器应能请求更多证据，或检查其他位置。将求解器限制在不完整候选集合内，可能把原本可以补救的定位遗漏变成无法避免的修复失败。

## 编程语言与缓存限制

M1 将代码视为文本，从任务文本中提取类似 ASCII 标识符的关键词。任务没有匹配关键词时，可能不会产生候选。它不解析 C++ 类型、重载、宏、条件编译、模板实例化或构建配置。文本关系是搜索线索，不是由编译器推导的调用图。编译器语义和构建元数据需要另行界定范围的扩展。

应将本地基线与未来模型和提示词缓存分别评估。已预热的仓库索引、操作系统缓存、模型前缀缓存和此前构建的仓库记忆属于不同条件。未来的持久化证据或摘要必须携带版本身份、检测过期状态，并在必要时回到当前源码检查。

## 设计依据

紧凑仓库上下文已有直接先例。[Aider 的仓库映射（英文）](https://aider.chat/docs/repomap.html) 展示了有预算限制的结构化上下文。[The Complexity Trap（英文）](https://github.com/JetBrains-Research/the-complexity-trap) 启发了与简单观察遮蔽方法进行比较。[Cost-Effective Repository Exploration（英文）](https://arxiv.org/abs/2608.29675) 启发了可测量的探索边界和可恢复的候选交接。Jev Scout 的价值必须通过评测确立，不能从这些研究的结果中推断。
