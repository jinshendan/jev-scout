# Jev Scout 路线图

[English](roadmap.md) · [简体中文](roadmap.zh-CN.md)

各个里程碑将可检查的基线与后续的智能体能力分开。每个里程碑都说明交付内容和完成标准；尚未交付的组件与性能收益不视为已经存在。

实现进度见 [M1](https://github.com/jinshendan/jev-scout/issues/1)，Jev 适配器见 [M2](https://github.com/jinshendan/jev-scout/issues/2)，受控修复评测见 [M3](https://github.com/jinshendan/jev-scout/issues/3)，仓库记忆见 [M4](https://github.com/jinshendan/jev-scout/issues/4)。项目定位与组件关系见[项目介绍](../README.zh-CN.md)和[架构说明](architecture.zh-CN.md)。

## M1 — 离线证据调查器

**当前范围：** Python 3.11+，在支持的 POSIX 系统上使用标准库实现；确定性规则；只读检查本地仓库；有界扫描、读取、步骤数和工作上下文；结构化证据与便于阅读的报告。

**交付状态：** 已通过 [PR #5](https://github.com/jinshendan/jev-scout/pull/5) 合并。CLI、安装包、测试与 CI 已在 `main` 上提供。

```sh
scout investigate --repo PATH --task TEXT --output DIR \
  --max-steps N --max-context-chars N
```

生成的文件：`events.jsonl`、`evidence.json` 和 `report.md`。

完成标准：

- 无需模型凭证或网络访问，即可从本地仓库生成可检查的产物。
- 遵守资源限制，并明确披露截断、部分检查和预算耗尽。
- 原始观察独立保存，不因工作上下文中的记录被移出而丢失。
- 将证据关联到源码位置和预期的内容标识。
- 区分错误、部分结果与成功完成的检查。
- 测试确定性决策、预算、证据恢复、源码访问边界和产物一致性。

M1 是用于调查的规则基线。它不会解决 issue、确定完整根因、验证补丁、续跑先前的调查、跨任务学习，也不提供经过校准的置信度。

## M2 — Jev 集成

**进行中：** 通过决策策略接口接入 Jev，同时将证据采集与修复求解器接口分开。M2 分为几个范围明确的增量；仅有一个可用的适配器，并不意味着整个里程碑已经完成。

### M2a — 类型化候选选择与用量记录

**已交付范围：** 基于标准库实现的可选适配器，连接官方 TypeSafe 接口；默认仍使用离线规则策略。已通过 [PR #6](https://github.com/jinshendan/jev-scout/pull/6) 合并，并在 `main` 上提供。

本增量已实现：

- 将所有尚未查看的具体候选 ID、任务文本和当前上下文提交为一个 Choice 问题。
- 固定默认模型版本、可配置的置信度下限，以及仅从环境变量读取的凭证。
- 请求与响应的字节限制、服务调用预算、套接字操作超时，以及不自动重试的行为。
- 在本地验证选择是否属于允许的候选集合；对于无效、不可用、低于置信度门槛或超出预算的请求，显式回退到规则策略。
- Schema 2 产物，包含可检查的请求内容、决策轨迹、模型版本、延迟，以及允许为空的服务端 token 用量。
- 无需凭证的受控 HTTP 测试，用于验证请求与响应协议及失败路径。

验收检查：离线基线仍可运行；未知 ID 不能执行动作；回退不会丢失源码观察；无效响应和服务限制会留下可见轨迹；密钥和错误响应正文不会进入产物。

尚未验证带凭证的真实服务运行。M2a 提供的是可测试的适配器契约，尚未测得它相对于规则策略的收益。详见 [Jev 策略指南（英文）](jev-policy.md)和 [ADR 0002（英文）](adr/0002-typed-jev-decisions.md)。

### M2b — 显式恢复与冻结输入下的策略比较

**本增量已实现：** 按 ID 恢复已保留的观察，并在一次有界源码捕获的基础上，比较两个独立的策略运行。详见[证据恢复指南（英文）](evidence-recovery.md)、[策略比较指南（英文）](policy-comparison.md)和 [ADR 0003（英文）](adr/0003-recovery-and-frozen-comparisons.md)。

**交付：** [PR #7](https://github.com/jinshendan/jev-scout/pull/7)。

```sh
scout recover --evidence PATH --repo PATH --observation ID --output DIR \
  --max-context-chars N
scout compare --repo PATH --task TEXT --output DIR \
  --max-steps N --max-context-chars N --challenger rule
```

已交付范围：

- 有界导入 Schema 1 或 2 的证据，并由调用者显式指定仓库。
- 保留历史记录，核对内容哈希、源码范围和摘录；只有与当前源码匹配的记录才会进入有界上下文。
- 规则组与挑战者组共享一次捕获的候选集合和源码内容，同时各自保有独立的策略状态与轨迹。
- 快照标识、单独的当前工作区复核、准备阶段与各组运行的计时，以及服务用量和回退记录。
- 离线的规则对规则一致性检查；通过显式指定 `--challenger jev` 进行需要凭证的比较。

验收检查：可以重新请求被移出上下文的观察，同时保留原始摘录；已变化、不可用或遭篡改的摘录不能进入当前上下文；产物中的仓库元数据不能扩大源码访问范围；即使工作区发生变化，两组仍读取同一份已捕获的源码；冻结证据不会声称当前源码仍有效；未知的服务用量仍明确标为未知。

本增量提供比较机制，尚未完成真实 Jev 验证，也没有策略质量结论。顺序捕获不是原子性的仓库快照。恢复需要手动请求，不会续跑原调查，也不会生成更多候选。

### M2 剩余工作

以下内容仍在计划中：

- 由策略请求更多证据，并自动恢复被移出上下文的观察。
- 自适应生成候选，同时明确检查覆盖范围与源码版本。
- 利用共享输入的比较工具，在公开说明的任务集上进行真实的规则与 Jev 调查运行。
- 带凭证验证服务，并报告模型行为和实际用量。
- 将调查轨迹与后续工作关联起来。

完成标准：发布带凭证的规则与 Jev 比较，使用相同的源码输入、候选、限制和证据契约，并报告服务行为与用量。对于无效或不可用的服务响应，必须提供显式回退。可检查的轨迹应支持证据扩展，以及与后续工作的关联。不预设任何基准收益。

## M3 — 固定修复求解器与受控评测

**计划中：** 将调查结果接入固定的 LLM 修复求解器，并在可复现的评测环境中比较策略。

交付内容：

- 固定模型、提示词、工具、数据集和环境配置。
- 设置普通搜索、观察屏蔽、摘要和 Scout 证据交接等基线。
- 记录整个流程的成本与延迟，包括失败尝试、升级调用和上下文构建。
- 提供逐实例结果、失败分析，以及任务和仓库两个层面的不确定性。
- 将按条件扩展证据或升级模型的方案，与固定资源分配策略进行比较。

完成标准：发布可复现的成功率与成本比较，并说明局限。负面结果同样有价值；仅仅减少提示词长度，不能证明成本效益或正确性更好。

## M4 — 长期仓库记忆

**计划中：** 在单任务评测稳定后，沿按时间排序的任务序列，探索针对特定仓库的记忆机制。

交付内容：

- 以证据为依据的记忆，包含版本标识、刷新规则和显式失效机制。
- 针对过期、冲突、稀疏或无关记忆的检索与回退。
- 分开记录冷启动构建成本与摊销后的维护成本。
- 按时间顺序评测，防止后续修复或评测标签进入更早的调查。

完成标准：说明记忆在何时有益、何时有害，以及需要多少任务量才值得承担构建成本。该评测方向与标准的单任务排行榜结果分开呈现。

## 决策门槛

只有在前一阶段的接口可检查、评测可信之后，才增加复杂度。编译器语义、多智能体编排、托管服务和自动修复都应等到具体使用场景需要时再引入。尤其是，未经过编译器支持的验证，不能把基于文本的 C++ 检查宣传为语义理解。

仓库记忆已有直接相关工作：[Improving Code Localization with Repository Memory](https://arxiv.org/abs/2510.01003)。后续的 Jev 记忆组件必须与此类方法比较；将记忆、搜索和路由组合起来，本身不构成创新性声明。
